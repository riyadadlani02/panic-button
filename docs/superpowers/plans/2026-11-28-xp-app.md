# XP-Style Desktop App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** A Mac app (`.dmg`) that looks like a Windows XP program and lets a non-technical owner set up accounts, run the guard, answer its questions, press, run the check-up and read reports, without a terminal.

**Architecture:** `panic/app/` holds a Python bridge that runs the existing `panic` commands in a worker thread with their prompts and output routed to the window, a controller for the guard thread, Keychain unlock, and a pywebview window over a local page styled with vendored XP.css. A build script makes the `.app` with PyInstaller and the `.dmg` with `hdiutil`.

**Tech Stack:** Python 3.12, pywebview 6.x, keyring 25.x, PyInstaller 6.x, XP.css 0.2.6 (MIT, vendored), pytest.

**Spec:** `docs/superpowers/specs/2026-11-28-xp-app-design.md`

## Global Constraints

- App dependencies (`pywebview`, `keyring`, `pyinstaller`) go in a separate uv dependency group `app`; the CLI's runtime dependencies do not change and `uv run pytest -q` keeps passing without the group installed (app tests skip cleanly when pywebview is missing; the bridge itself must not import pywebview).
- One engine: the app calls `panic.cli.main([...])` and the existing connectors; no rule is re-implemented in the app.
- Keychain service name `panic-button`, account = the vault's absolute path. "Remember on this Mac" defaults on.
- No network listener; the page talks to Python only through pywebview's in-process JS API.
- Organisation accounts never show item contents in the app.
- XP.css is vendored with its MIT licence file; no CDN at runtime; the app icon is original artwork.
- Commits authored by Riya Dadlani only; no co-author or "generated with" lines.

## Review Focus

- A prompt routed to the window must never be answered by a stale or default value (a hung dialog must not auto-answer "y").
- Two commands must not run at once; a guard press and a manual press must not interleave.
- The passphrase must never be logged, printed, written to disk outside the Keychain, or returned to the page.
- Stopping the guard or quitting must stop it within a couple of seconds and leave the vault consistent.
- Questions answered in the app must reach the guard exactly like the dialog answers do (same keys, same effect).

### Task 1: Bridge, unlock and guard controller (no GUI)

**Files:** create `panic/app/__init__.py`, `panic/app/bridge.py`, `panic/app/keychain.py`, `panic/app/guard_thread.py`; tests `tests/test_app_bridge.py`.

**Interfaces (produced):**
- `Job`: runs `panic.cli.main(argv, ...)` in a thread. While it runs, `input`, `getpass.getpass` and `print`/stdout/stderr on that thread are routed to the job: prompts become events `{"type": "prompt", "id", "text", "secret": bool}`; output becomes `{"type": "output", "text"}`; end is `{"type": "done", "code"}`. `job.events(since)` returns new events; `job.answer(prompt_id, value)` releases the waiting prompt; `job.cancel()` makes the waiting prompt raise `EOFError` (the CLI prints "Cancelled."). Routing is per thread, so other threads are unaffected.
- `Runner`: at most one `Job` at a time (`busy` error otherwise); the passphrase prompt is answered from the unlocked session without reaching the page.
- `keychain.get(vault) / set(vault, pw) / delete(vault)` over `keyring`, service `panic-button`; injectable backend for tests.
- `GuardThread(vault, keyfile, passphrase, on_question, on_notice)`: runs `cmd_guard` through `panic.cli.main(["guard", ...], asker=..., notifier=..., sleep=...)` with an asker that turns each dialog into a question for the app (`open_dialog` returns a handle; `answer(handle)` returns the app's answer or None) and a sleep that wakes on stop; `start()`, `stop(timeout=3)`, `running`, `questions()` (open ones with account, text, deadline, handle), `answer(handle, "accept"|"lock")`.

- [ ] Tests first (fake connectors as in `tests/test_cli.py`): a scripted `arm --guided` job emits prompts and finishes with code 0 after answers; `cancel()` ends a waiting job with "Cancelled."; a second job while one runs is refused; the passphrase never appears in events; keychain set/get/delete with a fake backend; guard thread with a planted trigger produces one question, `answer(…, "lock")` leads to a press, `stop()` returns within 3 s.
- [ ] Implement; full suite; commit `feat: app bridge runs panic commands with prompts routed to the window`.

- Screens per the spec sketch: unlock (passphrase + "Remember on this Mac"), Home (accounts, PANIC with confirm, guard switch, last check, question count), Questions, Setup wizard (drives a `setup`/`arm` job: shows each prompt as an XP dialog with the right input), Check-up (drives a `checkup` job), Reports (list + view). Output from jobs shows in an XP window with a scrolling text area.
- [ ] Build it; preview the page in a browser with `dev-api.js` at desktop and small window sizes; keyboard focus visible; commit `feat: app screens in Windows XP style`.
